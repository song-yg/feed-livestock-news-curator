* `naver_collector` `_extract_press` 코드 리뷰 반영 (2026-07-15): `www.` 제거 방식을 `.replace("www.", "")`에서 `startswith` 체크 후 슬라이싱으로 변경 — 기존 방식은 도메인 문자열 어디에 있든 매칭돼서, 서브도메인 이름 중간에 우연히 "www."가 들어간 경우(드물지만 가능) 의도치 않게 지워질 위험이 있었음. 순수 개선이라 바로 반영. 같이 제기된 **서브도메인 통합**(예: `biz.yna.co.kr`/`www.yna.co.kr`을 같은 언론사로 인식 — 3.2 `PRESS_DEDUP_CAP` 정확도에 영향 가능) 이슈는 검토 후 **보류로 결정**: 한국 도메인 특유의 복합 접미사(`.co.kr`/`.or.kr`/`.go.kr` 등) 때문에 간단한 규칙으로는 정확히 처리가 안 되고 `tldextract` 같은 신규 의존성이 필요한데, 아직 실제 수집 데이터에서 이게 dedup 정확도를 왜곡하는 사례가 확인된 바 없어(이론적 가능성만 있음) 이 프로젝트의 기존 철학(확인된 패턴만 대응, 일반화 규칙은 미리 안 만듦 - `FALSE_POSITIVE_FILTERS`/`EXCLUDED_TERMS`와 동일 원칙)대로 실측 근거가 나오면 그때 대응하기로 함 (아래 "7. 아직 결정 안 된 것들"에 항목 추가).

* `gdelt_collector` 실행 테스트 메모(2026-07-14): 키워드 5개 중 4개(avian influenza / foot and mouth disease / feed price / livestock market) 정상 수집 확인. "HPAI"는 GDELT API가 "검색어가 너무 짧다"는 자체 에러로 거부 — 코드 버그 아니라 API 쿼리 제약. 키워드 리스트 확정 작업 때 함께 재검토 예정 (짧은 약어는 더 긴 표현으로 교체 검토). 또한 거의 매 호출마다 429(rate limit)가 발생해 총 실행 시간이 약 1시간 가까이 걸렸던 문제를 확인 — `REQUEST_INTERVAL` 8초→15초 상향, 재시도 로직을 "호출별 개별 대기"에서 "전역 공유 쿨다운" 방식으로 변경해 대응함. **실측치 추가(`main.py` 최초 전체 파이프라인 실행, 2026-07-14)**: 위 대응 이후에도 이번 실행에서 429가 26회 발생했고, GDELT 수집에만 약 78분이 소요됨(전체 실행 시간의 대부분을 차지) — 완전히 해소된 문제는 아니라는 뜻이라 "9. 소스 실패 대응" 백로그에 재검토 우선순위로 남아 있음.

이 과정에서 **국내(네이버)는 KST, 해외(GDELT+WATT)는 UTC**로 시간대를 통일하는 원칙을 명시적으로 확정함 — 네이버는 API가 이미 정확한 `+09:00`을 주고, GDELT는 이미 UTC 타임스탬프를 정확히 보유하고 있었으므로 WATT만 고치면 이 원칙이 전체적으로 일관되게 성립.



**공통 규칙 (모든 collector가 공유)**

* 요청 헤더: 봇 이름 + 연락처 명시된 UA 하나로 통일
* 요청 간격: 같은 호스트에 연속 요청 시 최소 텀 유지 (사이트 부담 최소화)
* 출력 형식: 소스가 달라도 **동일한 스키마**로 맞춰서 다음 단계에 넘김 → `{source, title, url, published_at, category, body(optional)}`

  * `body`는 본문을 확보한 소스(WATT 계열)만 채움. 나머지 소스는 비워둠

## 2. 정제/정규화 레이어 (Normalizer)

* 각 수집기가 뱉은 서로 다른 원본 구조를 하나의 공통 스키마로 통일
* **완전 동일 기사 제거**: 같은 URL이 중복 수집된 경우(페이지네이션 겹침, 재실행 등)만 제거 대상
* 날짜 형식 통일, 결측치 처리 (예: GDELT는 본문 없음 → body 필드 비워둠)

### 2.1 이슈 그룹핑 (중복 제거 아님) — 키워드 사전 + 임베딩 하이브리드 매칭

같은 이슈를 국내(네이버)·해외(WATT) 매체가 각자 다루는 경우, 기사를 지우지 않고 하나의 이슈 그룹으로 묶는다. 이 매칭은 **키워드 사전과 임베딩, 두 메커니즘이 역할을 나눠 함께 작동**하는 하이브리드 구조다 (둘 중 하나만 켜는 선택지가 아니라, 아래처럼 처리 순서가 정해진 파이프라인).

|단계|메커니즘|역할|
|-|-|-|
|1차|KR↔EN 키워드 사전 (예: "조류독감"/"AI" ↔ "avian flu"/"HPAI")|명백한 매칭을 빠르게 잡아내는 필터. 계산 비용 거의 없음 (※ 실제 구현에서는 사전이 빈 상태로 확정됨 — 아래 "구현 현황" 참조)|
|2차|다국어 임베딩(BGE-M3)|1차에서 못 잡은 나머지 전체를 의미 기반으로 매칭. 사전에 없는 신규 표현·의역된 제목까지 커버|
|3차|LLM 그룹핑 보조 (4번 섹션 (B))|임베딩 유사도가 임계값 근처(애매 구간)인 경우만 최종 판단|

즉 사전이 "빠르고 확실한 것"을 먼저 걸러내고, 임베딩이 "사전으로는 못 잡는 나머지"를 커버하며, LLM은 그중에서도 "임베딩만으로 애매한 경계선"만 보조하는 구조다. 언어가 다른 기사끼리도 매칭해야 하므로 임베딩은 다국어 모델을 사용한다.

**모델**: `BAAI/bge-m3` (오픈소스, MIT 라이선스, 100개+ 언어 지원, 한국어 포함). `sentence-transformers` 또는 `FlagEmbedding` 라이브러리로 로컬 실행 — API 과금 없음, GPU 불필요.



**작동 방식**

1. KR↔EN 키워드 사전으로 명백한 매칭을 1차로 걸러냄 (위 표 1차 단계)
2. 1차에서 매칭 안 된 나머지 기사를 대상으로, 모든 기사(제목 + 있으면 본문 요약 일부)를 BGE-M3로 벡터화
3. **전체 기사 벡터 × 전체 기사 벡터** 코사인 유사도 계산 (2026-07-13 확정 — 기존엔 "국내×해외" 교차매칭만 정의돼 있었으나, 국내-국내(네이버 내 동일 사건 중복 보도)·해외-해외(WATT 사이트 간 중복) 케이스도 놓치지 않도록 전체 매칭으로 범위 확대. 어차피 전 기사를 벡터화하므로 비교 대상 필터만 바뀌는 것이라 계산 비용 문제는 없음)
4. 임계값(threshold) 이상 → 같은 이슈로 자동 그룹핑
5. 임계값 근처 애매한 구간만 4번 섹션의 **(B) LLM 그룹핑 보조**로 넘겨 최종 판단 (전수 호출 아님)
6. 그룹의 `mention_count` = 묶인 기사 개수 그대로 → 다음 단계 언급빈도 계산에 원본 그대로 반영 (버려지는 언급량 없음)
7. 그룹 안에 속한 기사들의 제목·원문 링크는 전부 보존 → LLM 요약 단계에서 그룹 내 여러 제목을 함께 입력해 하나의 종합 요약 생성, 결과물에는 요약 하나 + 원문 링크 여러 개를 같이 노출



**참고**: 임베딩은 매칭(같은 이슈인지 판단)만 수행하며 번역은 하지 않는다. 벡터 유사도로 "조류독감"과 "avian flu"가 같은 내용임을 판단할 수는 있지만, 그 결과물은 벡터(숫자)일 뿐 번역된 텍스트가 아니다. 한국어 요약·번역이 실제로 필요한 지점(4번 섹션 (A), "12. 언어 처리 방침" 섹션)은 전적으로 LLM이 담당한다.



**임계값**: 정확한 수치는 미확정 — 최종 확정은 여전히 사람 판단 필요 (→ "7. 아직 결정 안 된 것들" 참조). `issue_grouper.py`에는 `THRESHOLD=0.75`, `BORDERLINE_MARGIN=0.05`가 **잠정값**으로 들어가 있음(`scorer.py`의 `PRESS_DEDUP_CAP`과 같은 성격 — 확정 전까지 파이프라인을 돌려보기 위한 임시 상수). 2026-07-15 재검증 결과, 실제 국내-해외 교차 매칭 후보와 오탐 위험 쌍이 거의 같은 유사도 구간(0.71~0.75)에 겹쳐 있어 숫자만으로 깔끔하게 결정하기 어렵다는 게 확인됨 — **3차 LLM 보조는 2026-07-15에 구현 완료**돼 이 애매 구간을 실제로 처리하고 있으나(아래 "구현 현황" 참조), 임계값/마진 수치 자체의 최종 확정은 여전히 사람 판단(시범 운영 결과 보고 결정) 영역으로 남아 있음. 이 레이어는 계산(벡터 유사도)만 하므로 **LLM 안 씀** — 4번의 (B)만 애매 구간 보조로 관여.



**구현 현황 (2026-07-15, `issue_grouper.py` + `main.py` 연결 완료)**

* **1차 사전(`ISSUE_SYNONYM_GROUPS`)은 빈 리스트로 확정됨**: 애초엔 위 표 예시처럼 "조류독감"/"AI" ↔ "avian flu"/"HPAI" 같은 질병명 단위 묶음으로 채워서 시도했으나, 실제 재검증(`calibrate_issue_grouper.py` 실행) 결과 이 방식이 이슈 그룹핑의 정의("동일 사건만" — 아래 참조)와 맞지 않는다는 게 확인됨. 예: "조류독감" 묶음이 국내 기사 1건과 필리핀/캄보디아/호주/미국 등 전혀 다른 나라의 bird flu 기사를 전부 한 그룹으로 묶어버렸고, "구제역" 묶음도 한국 예천 발생 기사와 남아공 FMD 백신 관련 기사가 섞임(실측 로그 `calibration_log.txt`). "완전 동일 사건" 매칭은 국가/장소/시점까지 구분해야 하는 훨씬 좁은 단위라 질병명 키워드 매칭으로는 표현이 애초에 불가능하다는 결론 — 그래서 1차 사전은 비워두고 2차(BGE-M3 임베딩)에만 의존하는 구조로 전환함(인프라 자체는 남겨둠 — 나중에 더 구체적인 키로 다시 채울 가능성 대비).
* **이슈 그룹핑 정의를 "동일 사건만"으로 확정**: 한국 조류독감 발생과 미국 조류독감 발생은 같은 질병이어도 별도 이슈로 취급 (세계적으로 큰 이슈면 각 발생건이 각자 랭킹에 자연스럽게 올라올 것이므로 억지로 합칠 필요 없음). 이 정의로 생기는 "큰 트렌드가 개별 이슈로 흩어져 보이는" 공백은 이슈 그룹핑을 넓히는 대신 별도의 거친(coarse) 보조 지표(카테고리 전체 집계, `category_aggregator.py`, "11. 추가 고려 기능" 참조)로 메움.
* **병합 로직**: 1차/2차 매칭 결과를 Union-Find(합집합-찾기) 구조로 병합 — "A-B 매칭", "B-C 매칭"이 나오면 A/B/C를 최종적으로 한 그룹으로 묶는 표준 자료구조.
* **2-pass 버그 수정(2026-07-14, 재검증 완료)**: 기존엔 한 pass 안에서 "threshold 이상이면 union, 아니면 borderline 기록"을 같이 처리했는데, 이러면 두 기사가 직접은 threshold 미만이라도 다른 기사를 거쳐 간접적으로 이미 같은 그룹으로 묶인 경우까지 borderline에 중복 기록되는 문제가 있었음. 실측 재검증에서 "농협 2200억" 기사 54건이 이미 다른 연결로 한 그룹에 묶였는데도 그 내부 쌍들이 threshold 바로 아래라는 이유만으로 전체 borderline 쌍 446개 중 342개(77%)를 차지하는 게 확인됨 — 이미 결과가 확정된 쌍인데 LLM 보조 대상으로 잡혀서 "전수 호출 아님" 설계 의도가 실제 스케일에서 깨지는 원인이 됨. union을 먼저 전부 끝낸 뒤(간접 연결까지 확정) borderline 후보를 검사하도록 순서를 바꿔 재검증한 결과, borderline 쌍이 446개 → 70개로 줄어듦 (최종 그룹핑 결과가 실제로 달라지는 쌍만 남도록 수정됨).
* **`main.py` 연결 (2026-07-15)**: `scorer.to_singleton_groups()` 임시 처리를 실제 `issue_grouper.group_issues()` 호출로 교체. **그룹핑을 먼저, 국내/해외 축 분리는 그 다음** 순서로 구현 — 위 3번 항목(전체 기사 벡터 × 전체 기사 벡터)대로 국내-해외 교차 매칭이 가능하려면 축을 나누기 전에 전체 기사를 대상으로 그룹핑해야 하기 때문(기존 임시 코드는 축을 먼저 나눈 뒤 각각 싱글턴 그룹으로 처리하고 있어서, 그대로 바꿔치기하면 교차 매칭이 구조적으로 불가능해지는 문제가 있었음). 국내-해외 양쪽을 동시에 포함하는 그룹은 국내 축 스코어링엔 그룹 내 네이버 기사만, 해외 축엔 WATT/GDELT 기사만 걸러서 넘김(3.2 원칙대로 각 축의 원본 신호만 반영).

### 2.2 키워드 태깅

* 사전 정의한 `KEYWORDS_KR` / `KEYWORDS_EN` 리스트와 제목 매칭해서 어떤 이슈 카테고리인지 라벨링 (이슈 그룹핑과는 별개 — 카테고리 분류용)
* **어디에도 매칭 안 되는 경우**: `category: "기타"`로 라벨링하되, 기사 자체를 탈락시키지 않음 — 언급빈도 계산·이슈 그룹핑·LLM 요약 대상 선정은 다른 기사와 동일하게 진행
* `기타` 분류 건수를 결과물/로그에 노출하면, 키워드 사전이 최신 이슈를 잘 커버하고 있는지 보여주는 지표로 활용 가능 (비율이 늘면 사전에 신규 키워드 추가가 필요하다는 신호)
* **배포 전 테스트 기간에 사전을 직접 보강**해서 초기부터 `기타` 비율을 최대한 낮춰두면, 배포 이후 손볼 일이 그만큼 줄어듦
* **WATT 원본 category 처리 방식 (2026-07-14 확정, `keyword_tagger.py` 구현 중 결정 → 이번에 문서 반영)**: WATT 소스는 수집 단계에서 사이트 자체 카테고리(예: "Poultry", "Nutrition")를 이미 갖고 들어온다 — `WATT_collector.py`의 `_fetch_listing_page()`가 목록 페이지에서 "헤드라인 링크 바로 앞에 있는 링크"(`heading.find_previous("a")`)의 텍스트를 그 사이트의 카테고리로 추출하는 방식(위 "1. 수집 레이어" watt_collector 검증 범위 각주 참고). 이렇게 뽑힌 값은 2.2 태깅 단계에서 이 프로젝트 공통 카테고리 체계(질병명/시장가격/정부제도 등)로 `category` 필드가 덮어써지고, 사이트마다 분류 기준이 달라 이 프로젝트의 카테고리별 집계엔 안 맞기 때문. 정보 손실 방지를 위해 WATT의 원래 값은 `site_category` 필드에 별도로 보존한다. (naver/GDELT는 애초에 category가 비어서 들어오므로 해당 없음) — **2026-07-23 기준 활용 현황**: `site_category`는 저장은 되지만(raw.json에 그대로 포함) 집계·랭킹·요약 어디에서도 아직 적극적으로 안 쓰이는 상태 — 태깅 결과가 이상할 때 "원래 WATT는 이걸 뭐라고 분류했었나" 비교하는 디버깅 참고용 정도로만 존재.
  * **`site_category` 백업 조건의 부정조건 취약점 (2026-07-15, 코드 리뷰로 발견 — 대응 보류 결정)**: 현재 `keyword_tagger.tag_articles()`는 `article.get("source") not in ("네이버", "GDELT")`라는 **부정 조건**으로 "WATT 계열인지"를 판단한다. 새 소스가 추가되면 그 소스가 실제로는 WATT가 아닌데도 이 조건에 걸려 의도치 않게 `site_category`가 채워질 위험이 있음(예: 5.2 정부기관 보도자료 소스가 추가되면 이 조건에 걸림). 대안으로 `source in {"WATTAgNet", "Feed Strategy"}` 같은 긍정 조건이 제안됐음 — 실제 WATT 소스명이 문자열 `"WATT"`가 아니라 `"WATTAgNet"`/`"Feed Strategy"` 두 가지로 들어오므로(`WATT_collector.py`의 `SITES` 딕셔너리 키), 단순히 `source == "WATT"`로 바꾸면 오히려 한 번도 안 걸려서 `site_category`가 아예 안 채워지는 회귀가 생김 — 정확히 하려면 위 두 값을 명시한 집합으로 비교해야 함. 다만 **신규 소스 추가 계획이 현재 없어** 코드는 그대로 두기로 결정, 이 문서에 취약점과 올바른 수정 방향만 기록해둠 — 나중에 실제로 소스가 추가되면 그때 위 긍정 조건으로 교체.
* **"AI", "ND" 토큰 매칭 제외 (`keyword_tagger.py` `EXCLUDED_TERMS` 구현)**: 키워드표상 "AI"는 "조류독감"의 영문 축약형으로 등록돼 있으나, 실제 뉴스에서는 인공지능(Artificial Intelligence) 의미로 압도적으로 더 많이 쓰인다. 다른 표현(avian influenza/avian flu/bird flu/HPAI/LPAI/조류독감)이 이미 충분히 커버하고 있어, "AI" 하나 때문에 생기는 오매칭 위험이 더 크다고 판단해 실행 시점에만 매칭 대상에서 제외한다 (원본 키워드표 자체는 수정하지 않음 — `gdelt_collector.py`의 `FALSE_POSITIVE_FILTERS`와 동일한 철학: 확인된 위험 토큰만 대응, 일반화된 규칙은 안 만듦) (2026-07-14 확정)

  * **"ND" 추가 (2026-07-15 확정)**: "ND"는 "Newcastle disease"(뉴캣슬병)의 축약형으로 등록돼 있었으나, 2026-07-15 GDELT 실측 데이터(`calibration_raw_2026-W29.json`) 재검증 중 실제 오매칭이 확인됨 — "nd"가 "underway"/"Uganda"/"Andy"/"neighbourhoods"처럼 영어에서 아주 흔한 2글자 조합이라, 축산/사료와 전혀 무관한 기사 다수가 "질병명" 카테고리로 잘못 태깅됨(예: "National racing gets back underway at the GR Legends Rally" → `['ND']` 매칭). "AI"보다 오히려 충돌 빈도가 더 넓을 수 있는 케이스라 판단해 제외 목록에 추가함. 참고: "Newcastle disease"(풀네임)는 별도로 이미 등록돼 있어 "ND"를 빼도 뉴캣슬병 매칭 능력 자체는 유지됨(풀네임으로 언급되는 기사만 못 잡게 될 뿐). LSD/TMR 등 나머지 짧은 약어는 여전히 실제 오매칭 미확인 상태라 그대로 둠.
* **부분 문자열 포함 관계인 매칭 중복 집계 해소 (2026-07-20 신규)**: `CATEGORY_KEYWORDS` 전수 조사 결과 `feed cost`/`feed costs`, `corn`/`corn futures`/`CBOT corn`, `wheat`/`wheat futures`, `사료`/`배합사료업체`, `계열화`/`계열화사업법` 등 한쪽이 다른 쪽의 부분 문자열인 쌍이 27건 확인됨(담당자 발견). 제목에 "feed costs"가 있으면 `feed cost`와 `feed costs` 둘 다 매칭돼 그 카테고리의 매칭 개수가 인위적으로 부풀려지고, 이는 `tag_title()`의 "가장 많이 매칭된 카테고리 채택" 동점 처리 공정성에 직접 영향을 줌(부풀려진 카테고리가 실제로는 안 이겨야 할 경합에서 이길 위험). 사전(`CATEGORY_KEYWORDS`)은 원본 키워드표를 그대로 옮긴 것이라는 이 모듈의 원칙을 지키기 위해 사전을 고치는 대신, 매칭 집계 단계(`_dedupe_contained`)에서 "다른 매칭 항목에 완전히 포함되는 항목은 제외"하는 방식으로 해결 — 사전은 원본과 100% 동일하게 유지하면서, 더 구체적인 표현만 남기고 카운트는 정확해짐(예: `["corn", "corn futures", "CBOT corn"]` → `["corn futures", "CBOT corn"]`). `AI`/`ND`는 이미 `EXCLUDED_TERMS`로 처리돼 있어 이 27건에서 실질적 영향은 없었음.
* **'기타' 카테고리 샘플 출력 신규 (2026-07-17, `print_uncategorized_sample`)**: '기타' 비율이 실행마다 70% 넘게 나오는 게 반복 확인됐는데, 비율(숫자)만으로는 실제로 뭐가 몰리는지 감이 안 잡혀서 키워드 사전을 어떻게 보강할지 논의가 어려웠음. '기타'로 분류된 기사 제목을 최대 30건 그대로 로그에 출력하도록 추가 — 무작위 추출이 아니라 리스트 앞에서부터 그대로 보여주는 "감 잡기용" 진단 도구(`print_category_distribution`과 같은 성격, 통계적 대표성을 엄밀히 따지지 않음).

### 2.3 관련성 필터 (LLM, 2026-07-22 신설)

**배경**: 키워드 매칭만으로는 못 거르는 오매칭 유형이 실측으로 다수 확인됨 — ①동음이의어(질병명 `구제역`이 유튜버 닉네임과 겹침), ②검색어가 기관명/법안명 등 고유명사의 일부로만 등장(`축산`이 "농림축산식품해양수산위원회"라는 국회 상임위 이름 안에 있을 뿐인 정치 기사), ③각주성 언급(반도체 수출 기사 속 "육류 수출 191만달러" 한 줄). 이런 유형은 키워드를 아무리 좁혀도(복합어, `near()` 등) 구조적으로 해결이 안 되는데, LLM이 제목/요약 맥락을 읽으면 정확히 구분 가능한 문제라 별도 필터 단계로 신설함.

**위치**: 2.2 키워드 태깅 직후, 2.1 이슈 그룹핑(BGE-M3 임베딩 로드) 전. `relevance_filter.py` 신규 모듈, `filter_articles(articles)` 함수 하나만 노출. 이 단계에서 걸러지면 이후 임베딩 계산·3차 LLM 그룹핑 보조 대상도 함께 줄어드는 부수 효과가 있음.

**설계**: `issue_grouper.py`의 "3차 LLM 보조"와 동일한 패턴(프로바이더 스위치, 배치 호출, 실패 시 안전한 기본값 fallback) 재사용. 다만 기본값 방향이 반대 — 그룹핑 3차는 "애매하면 false(안 묶음)"가 안전하지만, 이 필터는 "애매하면 true(통과)"가 안전함(관련 있는 기사를 잘못 걸러내는 손실 > 무관한 기사 몇 개 더 통과하는 손실).

**소스별 컨텍스트 비대칭**: 네이버는 `description`(짧은 요약), WATT는 `body`(본문 앞부분)를 프롬프트에 줄 수 있지만, GDELT는 스펙상 본문이 없어(`body`가 항상 `None`) 제목만으로 판단해야 함 — GDELT 기사가 상대적으로 판정 근거가 부족하므로 실행 결과에서 특히 눈여겨봐야 할 대상.

**판단 기준(시스템 프롬프트에 반영)**: 사료 원료(옥수수·대두박·소맥 등 곡물, 사료첨가제)까지 "관련 있음"에 명시적으로 포함하고, 곡물이 사료 용도가 아닌 경우(식용·바이오에너지용)는 "관련 없음"으로 별도 명시 — 초안이 방역/질병/무역 위주로만 짜여 사료 산업 쪽 판단 기준이 약했던 걸 담당자 지적으로 보강함.

**배치 크기/id 매칭 (2026-07-22 실측 대응)**: 최초 30건/배치로 시작했으나, 실측 결과 무료 라우터(OpenRouter)가 30건 배치에서 출력 개수를 자주 못 맞춤(29건/31건 등)이 확인됨. 기존엔 "입력 개수 ≠ 출력 개수"면 배치 전체를 버리는 구조라 딱 1건만 어긋나도 29~31건이 통째로 낭비됨(담당자 지적 — "무쓸모"). 대응: 각 기사에 번호(`id`)를 매기고 모델도 그 id를 그대로 붙여 답하게 해서, 개수가 어긋나도 "몇 번이 빠졌는지" 정확히 알 수 있게 함 → 빠진 것만 안전한 기본값(통과)으로 처리하고 나머지는 정상 판정 그대로 사용(부분 복구). 배치 크기도 30 → 20(`issue_grouper.py`와 동일)으로 낮춰 애초에 어긋나는 빈도 자체도 줄임. 이 개선 이후 실측(파싱 실패율/실제로 걸러지는 기사 품질)은 아직 진행 전 — 다음 실행에서 확인 필요.

## 3. 언급빈도 × 최신가중치 계산 (Scoring)

```
issue_score = Σ recency_weight(기사의 경과일수)   ← 그룹 내 기사 각각 계산 후 합산
keyword_score = keyword_hit_count × recency_weight
```

※ keyword_score는 카테고리별 트렌드 시각화 및 민감 키워드 알림용으로 활용 가능성 검토 중 (현재는 미적용, 확정 시 추가 개발 필요)

* `recency_weight`는 그룹 내 **개별 기사마다** 자신의 발행일 기준으로 계산한 뒤 합산한다. (그룹 전체에 하나의 대표 날짜를 쓰지 않음 — 오래된 기사와 최근 기사가 섞인 그룹도 각 기사의 최신성이 점수에 그대로 반영되도록)
* `recency_weight`는 **계단형(문턱 함수)으로 확정**. 이유: 나중에 담당자가 값을 조정할 때, 수식 이해 없이 표의 숫자만 바꾸면 되도록 하기 위함

|경과일수|weight|
|-|-|
|0~2일|1.0|
|3~5일|0.7|
|6~7일|0.4|
|8일 이상|0.1|

```python
# recency_weight: 발행일로부터 경과일수에 따른 계단형 가중치
# 값 조정 시 이 표만 수정하면 됨 (공식 이해 불필요)
def recency_weight(days_elapsed: int) -> float:
    if days_elapsed <= 2:
        return 1.0
    elif days_elapsed <= 5:
        return 0.7
    elif days_elapsed <= 7:
        return 0.4
    else:
        return 0.1
```

## 4. LLM 사용 지점

"확실히 요약이 아니라고 판단할 수 있는 좁은 패턴만" 걸러내도록 대응 — 응답에 "user safety" 문구(대소문자 무관)가 포함되면 요약 대신 "본문 요약 생성 실패, 원문 제목만 노출"로 명확히 표시(`_is_suspicious_summary`). 품질이 낮거나 짧은 요약까지 거르는 건 이번 범위 밖 — 과도하게 넓히면 정상 요약도 걸러질 위험이 있어 실제로 관측된 문구만 좁게 대응함.

LLM은 딱 두 군데에서만 개입시키는 걸 추천:

|사용 지점|입력|출력|이유|
|-|-|-|-|
|**(A) 자체 요약 생성**|상위 랭크된 이슈들의 제목 + (본문 확보된 경우) 본문에서 뽑은 핵심 문장 + (네이버 소스인 경우) `description` 필드를 참고 컨텍스트로 추가(2026-07-13 확정 — 그대로 인용하지 않고 참고용으로만 사용) — 원문 그대로 아님|2~3문장 자체 요약|원문을 그대로 옮기면 저작권 리스크 중간단계로 상승 → 제목/핵심 내용만 보고 LLM이 새로 생성하는 게 안전한 대안|
|**(A-1) 얇은 재료 fallback**(2026-07-13 확정)|이슈 그룹핑이 안 되고 언론사 1곳만 보도한 단독 기사|LLM 요약 생성을 생략하고 원문 제목만 노출|재료(제목 하나뿐)가 너무 얇아 LLM이 요약을 만들면 사실상 제목을 부풀리는 것과 다름없어, 애초에 요약 대상에서 제외. 기존 9.4의 "출력 이상 시 fallback" 로직과 같은 계열의 조건 하나로 취급|
|**(B) 이슈 그룹핑 보조**|임베딩 유사도가 임계값 근처(애매 구간)에 걸린 기사 제목 쌍|"이건 같은 이슈다/다른 이슈다" 판단 (묶을지 말지 판단이지, 기사를 지우는 것 아님)|2번 레이어의 임베딩 유사도만으로 판단하기 애매한 경계선 케이스만 보조 호출 (전수 호출 아님, 비용 고려)|

LLM은 **원문 수집이나 크롤링 판단에는 관여 안 함** — 그건 순수 규칙(robots.txt, UA 등)의 영역.

* **raw.json의 실제 내용물 — "정제 전 원본"이 아님**: 원래 계획은 "정제 전 원본"이라고 적었지만, 실제로는 **2.5 관련성 필터까지 통과해 실제로 스코어링에 쓰인 최종 기사 데이터셋**을 저장하는 쪽으로 결정함 — 이름은 raw지만 "이번 주 분석에 실제로 쓰인 데이터"라는 의미. 수집 직후(필터링 전) 원본은 지금은 따로 안 남김.
* **WATT `body` 필드는 raw.json에서 제외**: `WATT_collector.py`에 이미 남아있던 "메모리에서만 사용 - repo 저장 시 제외(저장 레이어 책임)" 주석을 이행 — 스크랩한 기사 본문 전체를 공개 repo에 커밋하는 건 저작권상 바람직하지 않다는 판단.
* **scored.json은 각 이슈 항목에서 `articles`(원본 기사 dict 전체) 필드를 제외**: `scorer.score_group()`이 만드는 `articles` 필드를 그대로 저장하면 raw.json과 중복 저장되고, WATT body 저작권 문제도 재발함 - `issue_score`/`mention_count`/`titles`/`urls`/`press_list`/`summary` 등 요약 필드만 남김.
* **저장 방식 결정 — repo 커밋 (아티팩트 아님)**: 과거 주차 데이터로 "지난주 대비 변화"를 비교하려면, 다음 실행 시점에 checkout된 repo 안에 지난주 데이터가 그대로 남아있어야 함 - Actions 아티팩트는 보존 기간이 지나면 사라지고 다음 실행에 자동으로 안 딸려오므로 이 용도에 안 맞다고 판단. `run-pipline.yml`에 git commit/push 스텝 추가(`permissions: contents: write` 명시 필요, 기본 `GITHUB_TOKEN`이 repo 설정에 따라 read-only일 수 있음). `data/` 변경 사항이 없으면(예: 파이프라인 도중 실패) 빈 커밋을 안 만들도록 `git diff --cached --quiet`로 조건부 처리.
* **아직 실전 실행으로 검증 안 됨**: `storage.py` 자체 점검(단독 실행 시 `python3 storage.py`로 raw.json에서 body 제외/scored.json에서 articles 제외가 잘 되는지)은 통과했지만, 실제 GitHub Actions 실행에서 git commit/push까지 끝까지 성공하는지는 다음 실행에서 확인 필요.

```

 ├─ 1) 각 collector 순차 or 병렬 실행 (사이트별 예의상 순차 추천)
```

7. **오류 처리 매뉴얼 — GitHub 플랫폼 자체 장애 대응 (2026-07-21 신규)**

배경: 2026-07-19~20에 실행이 `Waiting for a runner to pick up this job...` 상태로 5분 넘게 멈춘 사례가 실제로 발생 — 우리 workflow/코드 문제가 아니라 GitHub 측 대규모 플랫폼 장애(Actions/API/Issues/Pages 동시 성능 저하)였음(위 "13. GitHub Actions 실행 자동화" 참조).

**왜 workflow 안에 자동 재시도 로직을 넣을 수 없는지**: 이 증상은 job이 **아예 실행을 시작하지도 못한 상태**(러너 배정 대기 중)에서 발생한다. workflow 내부의 재시도 로직(예: 특정 step을 몇 번 다시 시도하는 것)은 job이 실행되기 시작한 뒤에나 의미가 있는데, 이 문제는 그 이전 단계에서 멈춘 것이라 workflow 코드로는 손쓸 방법이 없다. 그래서 이건 코드가 아니라 **사람이 따라야 할 절차**로 정리한다.

**증상 확인 → 대응 절차**:

1. **증상 인식**: 실행이 `Waiting for a runner to pick up this job...`(또는 이와 유사하게 아무 진행이 없는) 상태로 평소보다(보통 수십 초~1분 이내 배정) 눈에 띄게 오래(5분 이상) 멈춰 있음
2. **원인 확인**: https://www.githubstatus.com 접속해서 Actions(및 관련 서비스) 상태 확인
   * **장애로 표시됨** → 우리 문제가 아님이 확정됨. 아래 3번으로.
   * **정상으로 표시됨** → 일시적 지연일 가능성이 높음, 몇 분 더 기다려보고 그래도 안 풀리면 아래 3번으로.
3. **대응**: 실행 취소(Cancel) 후, 상태 페이지가 정상으로 돌아온 뒤(또는 그냥 바로) 재실행(Run workflow). 자동 재시도가 없으므로 **사람이 직접 취소·재실행해야 함**.
4. **스케줄 자동 실행(향후 5~6단계 완료 후 적용 시)의 경우**: 이번 주 실행이 이런 이유로 실패해도, 다음 주 스케줄에 자동으로 다시 시도되므로 심각한 문제로 보지 않아도 됨 — 다만 "이번 주 실행이 통째로 안 됐다"는 걸 사람이 빨리 알 수 있도록 9.2(에러 리포트 자동화, 아직 미구현)와 함께 실패 알림을 붙이는 걸 권장(현재는 저장/배포 레이어 자체가 없어 알림도 없음 - 5~6단계와 함께 검토).
5. 지금(수동 실행만 쓰는 단계)은 위 1~3번을 사람이 직접 수행하는 것 외에 대응 방법이 없음 — 코드 개선의 여지가 원천적으로 제한적인 케이스임을 인지하고 넘어갈 것.

## 9.3 에러 유형별 대응 가이드 (표로 정리)

|에러 유형|원인|누가 고칠 수 있나|
|-|-|-|
|파싱 실패|사이트 구조 변경|코드 수정 필요 (개발자/외주)|
|401/403|API 키 만료 또는 크롤링 차단|API면 키 재발급(비개발자 가능), 차단이면 코드 수정|
|429|요청 과다로 일시 제한|대개 자연 해결|
|타임아웃|사이트 일시 다운|다음 주 재시도로 해결|
|빈 결과(에러 없이 0건)|조용히 깨진 경우, 가장 위험|**직전 N주 평균 대비 이번 주 수집량이 급감(예: 20% 미만)하면 "이번 주 실행 상태" 배지에 경고 표시로 자동 감지** (완전 자동 해결은 아니고, 사람이 놓치지 않게 하는 장치)|

* **한계**: 이 구조는 "부분 장애가 전체 장애로 안 번지게" 하는 것이지, 코드 수정이 필요한 근본 문제(파싱 실패, 차단)까지 자동 해결해주진 않음
* **실사례 메모 (2026-07-14)**: Feed & Grain에서 겪은 문제는 이 표의 "파싱 실패"도 "401/403"도 아닌 애매한 케이스였음 — 에러 없이 200번대 비슷하게 조용히 응답은 오는데(실제로는 403이었지만 겉보기엔 정상 흐름처럼 보였음) 내용이 매번 동일한 유형. "빈 결과"만큼 위험하진 않지만, 표에 없는 "조용히 같은 콘텐츠만 반복 반환" 케이스도 있을 수 있다는 걸 확인한 사례 — 당장 표를 확장할 필요는 없지만 참고로 남김

## 9.4 LLM 오작동 위험

* 위험 유형: 환각, 과잉 해석, 형식 붕괴, API 장애, "그럴듯한데 미묘하게 틀림"(가장 위험 — 사람이 대조 안 하면 못 잡음)
* 대응책:

  1. LLM 입력을 제목(+핵심 요약)으로 제한, "없는 내용 추가 금지" 명시
  2. 출력에 항상 원문 링크 강제 부착 → LLM 요약을 "안내문"으로만 쓰게
  3. 출력 형식을 코드로 자동 검증(항목 개수, URL 일치 여부, 언어 등) — 어긋나면 **요약 없이 원문 제목 리스트만 발송하는 fallback**으로 자동 전환
3-1. (2026-07-13 확정) 출력 이상이 아니어도, 이슈 그룹핑이 안 되고 언론사 1곳만 보도한 단독 기사는 애초에 LLM 요약 호출 자체를 생략하고 원문 제목만 노출 (재료 자체가 얇아서 발생하는 케이스라 3번의 "출력 이상 감지형" fallback과는 트리거 조건이 다름 — 4번 섹션 (A-1) 참조)
  4. LLM 요약과 원본 제목 리스트를 나란히 배치해 사람이 스치듯 비교 가능하게
  5. temperature 낮게, "확실하지 않으면 요약 대신 제목만 나열" 지시
* **한계**: 명백히 이상한 건 잡아내도, 미묘하게 틀린 건 구조적으로 못 막음 → LLM 요약은 "빠른 훑어보기용"이라고 문서에 명시하고, 진짜 판단은 항상 원문 링크로 가게 유도하는 게 현실적 목표

## 9.5 무료 모델 짜집기 vs 유료 API 안정성

* **유료 API(Anthropic/OpenAI)**: 모델 은퇴 전 최소 60일(Anthropic)~6개월(OpenAI, 일반 공개 모델 기준) 사전 공지 원칙. 모델 하나 은퇴해도 서비스 자체가 없어지는 게 아니라 최신 버전으로 갈아타면 됨
* **무료 모델/서비스**: 이런 공지 의무가 없는 경우가 많아 예고 없이 정책이 바뀌거나 서비스가 접힐 수 있음 — "여러 개 박아놓고 폴백"은 오히려 서비스 자체가 조용히 바뀌는 리스크를 못 막음
* **실무 제안**:

  1. 이 프로젝트 규모(주 1회, 제목/핵심요약 기반)면 유료 API 비용 부담이 크지 않을 가능성 높음 → 무료 짜집기보다 유료 하나로 단순하게 가는 게 유지보수엔 더 안전
  2. 모델 이름은 코드 여기저기 아니라 설정 파일 한 곳에서만 관리
  3. API 키 등록 이메일은 개인 메일이 아니라 팀 공용/복수 인원이 보는 메일로 — 은퇴 공지 놓치지 않게
  4. 무료로 갈 수밖에 없다면, 복잡한 자동 전환 로직보다 "실패 시 요약 없이 원문 링크만 발송" 쪽이 유지보수 부담이 훨씬 적음
* 참고로 이슈 그룹핑에 쓰는 BGE-M3는 로컬 실행 오픈소스라 이 은퇴 리스크 자체가 해당 없음 (API 호출이 아니라 다운로드해서 쓰는 모델)
* 유료 모델(Haiku 4.5, Sonnet 4.6 등): Haiku 4.5 기준 **월 1달러 미만**. 사실상 무시 가능한 수준.
* **실제 채택 사례 (2026-07-15, 3차 LLM 그룹핑 보조)**: 위 원칙대로 기본 프로바이더는 Anthropic(Haiku 4.5)으로 구현했으나, API 키 발급 결재가 지연되는 상황이 실제로 생겨서 "완전히 막혀서 검증을 못 하는 것"과 "원칙(유료 우선)" 사이에서 절충함 — `LLM_PROVIDER` 환경변수로 OpenRouter 무료 라우터(`openrouter/free`)를 켤 수 있는 스위치를 만들되, (a) 코드 기본값은 그대로 anthropic로 유지, (b) GitHub Actions 등 운영 환경에는 이 스위치를 쓰지 않는 걸 권장 문구로 남기고, (c) 승인 나면 환경변수만 지우면 원래 경로로 즉시 복귀하도록 설계함(위 실무 제안 2번 "모델 이름은 설정 파일 한 곳에서만 관리" 원칙 그대로 재사용). 즉 "무료 모델을 상시 운영에 쓰지 않는다"는 원칙은 유지하면서, "승인 대기 중 로컬/Actions에서 파이프라인 전체를 끝까지 한 번 검증해보고 싶다"는 실질적 필요는 임시 경로로 수용한 케이스. "2.1 이슈 그룹핑" 구현 현황 및 "13. GitHub Actions 실행 자동화" 참조.
* **폴백 체인 2단계 확장 (2026-07-28)**: 위 실무 제안 4번("복잡한 자동 전환 로직보다는...")과는 별개로, Anthropic 키 승인 전까지 임시로 쓰는 openrouter 경로 자체의 안정성을 조금이라도 높이기 위해 "지정 모델 실패 시 openrouter/free 1회 재시도"이던 걸 "지정 모델 → 2순위 모델(`OPENROUTER_MODEL_2`) → 3순위 모델(`OPENROUTER_MODEL_3`) → openrouter/free" 체인으로 확장함. 여전히 무료 모델을 여러 개 박아놓는다고 "서비스 자체가 조용히 바뀌는 리스크"까지 막아주진 않는다는 위 원칙은 그대로 유효 — 이건 어디까지나 승인 대기 중의 임시 경로를 조금 더 버티게 하는 보강일 뿐, 근본 해결책(Anthropic 키 승인)을 대체하지 않음. 상세 → 문서 맨 끝 "LLM 모델 폴백 체인 2단계 확장 (2026-07-28)" 항목 참조.

# 11. 추가 고려 기능

**바로 추가 가능 (부담 적음)**

1. 지난주 대비 변화 표시 (신규/지속 이슈 태깅) — 과거 파일과 제목 매칭만으로 가능, LLM 불필요
2. 발행 매체 다양성 카운트 (해당 이슈를 다룬 매체 수 표시)
3. "이번 주 실행 상태" 요약 배지 (예: "4개 소스 중 3개 정상", 수집량 급감 경고 포함) — 결과물 최상단에 노출
4. **카테고리 전체 집계 — 구현 완료 (2026-07-14, `category_aggregator.py`)**: 2.1 이슈 그룹핑의 정의를 "동일 사건만"으로 확정하면서(예: 한국 조류독감과 미국 조류독감은 별개 이슈) 큰 트렌드가 개별 이슈로 흩어져 보이는 공백이 생김 — 이슈 그룹핑 자체를 넓히는 대신, `keyword_tagger.py`의 카테고리 라벨을 그대로 활용해 "이 카테고리(질병명/시장가격 등)가 이번 주 전체 몇 건 다뤄졌는지"를 보여주는 별도의 거친(coarse) 보조 지표로 추가함. 설계 결정 3가지:

   * **집계 방식 — 단순 건수** (recency_weight 미적용): 3번 섹션에 정의만 되고 미적용 상태인 `keyword_score`(개별 키워드 단위, recency_weight 가중)와는 단위·목적이 다른 별개 기능 — `keyword_score`는 여전히 미구현으로 남겨둠. 이 지표는 순위/선별용이 아니라 주간 개요용이라 가중치 없는 단순 건수가 더 투명함
   * **집계 범위 — 국내/해외 각각 별도** (3.1~3.2 기존 원칙과 동일, `scorer.split_domestic_international()` 재사용) — 이 지표만 통합하면 다른 결과물과 원칙이 안 맞음
   * **지난주 대비 증감 — 이번 범위 밖**: 저장 레이어(5번 섹션, 아직 미구현) 완성 후 위 1번 항목과 함께 별도로 붙일 것
   * `main.py`의 `[3-보조]` 단계로 연결 완료 (스코어링 Top N과는 독립적으로 실행)

**가치는 있으나 선결 필요**

5. 키워드 알림(민감 키워드 강조) — 키워드 사전을 누가 지속 관리할지 필요
6. 아카이브 검색 페이지(GitHub Pages) — 사실상 별도 프로젝트 규모, 여유 생기면 고려

**현재는 보류 (리스크 대비 이득 낮음)**

6. 감정/톤 분석 — LLM 판단 지점 추가로 오작동 리스크 표면적 증가
7. 자동 번역 — 오역 리스크 신규 발생 ("12. 언어 처리 방침"과 배치)

# 12. 언어 처리 방침 (한글/영어 소스 혼재 대응)

## 12.1 제목

* 네이버(한국어) 소스: 원문 그대로
* WATT(영어) 소스: **영문 제목 원문 유지 + 필요시 짧은 한글 보조 설명 병기** (전체 번역 금지)
* GDELT 소스: **원문 제목 언어와 무관하게 동일 규칙 적용** — 원문 제목 유지 + 필요시 짧은 한글 보조 설명 병기 (전체 번역 금지)

  * 2026-07-14 진단 확인(`test_gdelt_collector.py`, `_print_distribution`): GDELT는 영문 키워드로 검색해도 반환되는 기사의 `title`이 항상 영어인 것은 아님 — 독일어/러시아어/중국어/터키어/아랍어 등 원문 스크립트 그대로 오는 경우가 실측으로 확인됨 (article_search가 title을 번역 없이 원문 그대로 반환하기 때문, `gdelt_collector.py` "language"/"sourcecountry" 필드 참고)
  * 즉 위 "WATT/GDELT = 영문 제목" 전제는 GDELT에는 정확히 들어맞지 않으므로, GDELT는 "영어 소스"가 아니라 "다국어 소스"로 취급한다 — 제목이 어떤 언어든 원문 그대로 유지하고, 한국 독자가 못 읽는 언어(중국어/러시아어 등)라도 임의로 삭제하거나 영어로 대체하지 않는다
  * 이슈 그룹핑(2.1)에서 매칭되면 어차피 국내(네이버) 또는 WATT 쪽 제목과 함께 그룹으로 묶여 LLM 요약(4번 (A))이 한국어로 생성되므로 원문 제목 언어는 문제가 되지 않음
  * 매칭 안 되고 단독 기사(4번 (A-1) fallback)나 5.1 대표기사로 노출되는 비영어 GDELT 제목은, 원문 제목 그대로 노출하되 **짧은 한글 보조 설명을 반드시 병기**해 한국 독자가 최소한 무슨 내용인지는 알 수 있게 한다 (병기 문구는 LLM이 제목만 보고 1줄 생성 — 본문 요약처럼 확인 안 된 수치·고유명사를 임의로 채우지 않도록 4번 (A) 안전장치와 동일 기준 적용)

## 12.2 본문 요약 (WATT 등 본문 확보 소스)

* 본문 요약은 한국어로 생성하되, 요약 과정에서 번역이 개입되므로 아래 안전장치 적용:

  1. 본문을 그대로 직역하지 말고 핵심 내용만 한국어로 새로 요약 (저작권 리스크 및 번역투 동시 방지)
  2. **전문용어·질병명·정부기관명·제도명 등 고유명사는 임의로 한글화하지 말고 영문 원어를 괄호 병기** — 오역이 있어도 사람이 원어를 보고 바로 확인 가능하게 함
  3. 확실하지 않은 수치·전문용어는 임의로 해석하지 말고 원문 표현 유지
  4. 원문 링크 필수 부착 원칙은 기존과 동일하게 유지

## 12.3 근거

* 주요 모델(GPT/Claude/Gemini)의 일반적 한국어 성능은 영어와 체감 차이가 거의 없는 수준까지 개선된 것으로 알려져 있음
* 다만 방언, 신조어, **한국 고유 전문용어**(법률·행정·업계 특유 표현)에서는 여전히 오류 가능성이 있다고 알려져 있음 — 학습 데이터 내 한국어 비중이 영어 대비 낮은 것이 근본 원인으로 지목되나, 모델별 정확한 비중은 비공개라 구체적 수치는 확인 불가
* 사료·축산업 맥락에서는 일반 뉴스 문장은 리스크가 낮으나, 질병명/정부 고시명/한국 특유 제도명 등 전문용어는 여전히 오역·오용 위험 구간 → 위 "본문 요약" 안전장치가 이 리스크를 직접 완화하는 장치

# 13. GitHub Actions 실행 자동화 (수동 실행 workflow)

**신규 생성 (2026-07-15)**: `.github/workflows/run-pipeline.yml`. 로컬에서 `main.py` 전체 실행이 체감 2시간 정도 걸려서(9번 섹션 실측 - GDELT 수집만 최대 78분 걸린 사례 있음), 로컬을 붙잡고 있지 않고 GitHub Actions에서 대신 돌릴 수 있게 만듦.

**트리거**: 지금은 `workflow_dispatch`(Actions 탭 > Run workflow 수동 버튼)만 켜뒀음. 6번 섹션 방침("트리거(스케줄/수동 버튼) 분리는 5~6단계가 실제로 구현된 뒤 함께 작업할 예정 — 현재는 아직 손대지 않음")을 그대로 따른 것 — `schedule`(예: 매주 월요일 자동 실행) 블록은 workflow 파일에 주석으로만 남겨뒀고, 5~6단계(저장/배포) 구현 완료 후 주석만 풀면 바로 켤 수 있음(4단계 LLM 요약은 2026-07-16 구현 완료).

**job 구성**:

1. 리포 체크아웃
2. 실행 전 디스크 사용량 확인 (`df -h /`, 아래 "디스크 부족 이슈" 참조)
3. 사용 안 하는 프리인스톨 툴 정리 (`.NET`/`Android SDK`/`GHC` 삭제)
4. Python 3.11 설치 (pip 캐시 포함)
5. PyTorch(CPU 전용) 우선 설치
6. `requirements.txt` 설치
7. Playwright Chromium 설치 (`watt_collector`가 브라우저 엔진으로 페이지를 로드하므로 필요)
8. apt 캐시 정리 + 설치 후 디스크 사용량 확인
9. BGE-M3 모델 캐싱 (`actions/cache`, 2.1 섹션에 있던 캐싱 설정 그대로 재사용 - 경로 `~/.cache/huggingface`, 최초 1회만 다운로드)
10. `python -u main.py` 실행 — 필요한 Secrets/Variables는 "8. GitHub Actions 유의사항" 표 참조 (`-u`: 파이썬 stdout 버퍼링 비활성화, 2026-07-16 추가 - 아래 "stdout 버퍼링 이슈" 참조)

**`timeout-minutes: 240`**: 로컬 체감 2시간에 GDELT 429 재시도 변동분을 감안한 여유값.

**로그 확인**: 별도 아티팩트 업로드 스텝 없음 — GitHub Actions는 실행 중인 job의 각 스텝 로그를 기본적으로 실시간 스트리밍으로 보여주므로, `main.py`의 모든 `print` 출력(수집 건수, 스코어링 Top N, 카테고리 집계, 3차 LLM 보조 진행 상황 등)이 그대로 노출됨.

**디스크 부족 이슈 — 발견 및 해결 (2026-07-15)**: 최초 실행이 `System.IO.IOException: No space left on device`로 실패함. 검색으로 원인 확인: GitHub-hosted `ubuntu-latest` 러너는 여유 공간을 14GB만 보장하는데, `sentence-transformers`를 아무 설정 없이 설치하면 GPU(CUDA)용 PyTorch가 딸려오고(수 GB), 여기에 BGE-M3 모델(2.2GB)과 Playwright Chromium(`--with-deps`로 시스템 라이브러리까지 설치)이 더해지면서 예산을 초과한 것으로 판단됨. 실행 트리거가 사람이 수동으로 누르는 버튼이라 "여러 번 실행해서 누적된 것"은 아님 — 러너가 실행마다 완전히 새 VM이라 이전 실행의 흔적이 안 남기 때문.

* **대응 1 — 프리인스톨 툴 정리**: 이 프로젝트(Python 전용)에 안 쓰는 `.NET`/`Android SDK`/`GHC`를 job 초반에 삭제.
* **대응 2 — PyTorch CPU 전용 선설치**: `pip install torch --index-url https://download.pytorch.org/whl/cpu`로 미리 깔아서, 이어지는 `requirements.txt` 설치에서 GPU 버전이 새로 안 받아지게 함 (BGE-M3는 CPU로만 돌리므로 GPU 버전 자체가 불필요 - 2.1 섹션 "GPU 불필요" 참고).
* **대응 3 — 단계별 `df -h` 로그**: 정리 전/후, 의존성 설치 후 디스크 사용량을 로그에 남겨 다음에 비슷한 문제가 생기면 어느 단계인지 바로 보이게 함.
* **실측 검증 완료**: 정리 전 16GB 여유(72GB 중 56GB 사용, 79%) → 프리인스톨 툴 정리 후 35GB 여유(37GB 사용, 52%)로 19GB 확보 → 이후 PyTorch/requirements/Playwright 설치까지 에러 없이 통과해 `main.py` 실행 진입까지 확인됨. 근본 원인 진단과 조치가 실제로 맞았다는 게 실행 결과로 검증된 케이스.

**3차 LLM 보조 - OpenRouter 모델명 빈 문자열 버그 — 발견 및 해결 (2026-07-15)**: 디스크 문제 해결 후 `main.py`가 끝까지 실행됐으나, 3차 LLM 보조(애매 구간 66쌍)가 전부 `400 Client Error: Bad Request`로 실패함(로그: `provider=openrouter, model=, 대상 66쌍` - model이 비어있음). 원인 확인(GitHub 공식 문서): 리포 Variables에 **등록 안 한** `OPENROUTER_MODEL`을 workflow에서 `${{ vars.OPENROUTER_MODEL }}`로 참조하면, 환경변수 자체가 "안 생김"이 아니라 **빈 문자열로 채워져서** 파이썬에 전달됨. `issue_grouper.py`가 그동안 `os.environ.get("OPENROUTER_MODEL", "openrouter/free")`를 쓰고 있었는데, 이 패턴의 `default`는 키가 "아예 없을 때"만 적용되고 빈 문자열이 있으면 그 빈 문자열을 그대로 반환하기 때문에, 기본값(`openrouter/free`)으로 안 떨어지고 빈 모델명이 그대로 API로 나가 매 요청이 400으로 거부됨.

* **수정**: `os.environ.get(key, default)` → `os.environ.get(key) or default` 패턴으로 변경(`LLM_PROVIDER`, `OPENROUTER_MODEL` 둘 다 적용) - 빈 문자열도 falsy라 자연스럽게 기본값으로 대체됨.
* **결과**: `OPENROUTER_MODEL`을 리포 Variables에 등록하지 않은 상태 그대로 둬도(workflow의 `${{ vars.OPENROUTER_MODEL }}` 줄도 그대로 둬도) 이제 안전하게 `openrouter/free` 기본값이 적용됨 - 별도로 Variables 등록이 필요 없어짐.
* 이번 66쌍은 이 버그 때문에 전부 "안 묶음" fallback으로 처리됨(9.4 안전장치가 정상 작동해 파이프라인 자체는 안 죽었음) - 수정 후 재실행하면 실제 판정 결과를 볼 수 있음.

**3차 LLM 보조 - X-Title 헤더 한글 인코딩 버그 — 발견 및 해결 (2026-07-16)**: 위 모델명 버그를 고친 뒤 재실행했더니(`model=openrouter/free`로 정상 호출은 됨) 이번엔 애매 구간 59쌍이 전부 다른 원인으로 실패함: `UnicodeEncodeError('latin-1', '사료축산뉴스-이슈그룹핑-3차보조', 0, 6, 'ordinal not in range(256)')`. 원인: OpenRouter 요청에 붙인 선택적 식별 헤더(`X-Title`) 값을 한글로 넣어뒀는데, HTTP 헤더 값은 latin-1(ASCII 계열) 인코딩만 허용돼 한글을 표현할 수 없어서 발생. `requests.models.PreparedRequest.prepare_headers()`는 이 인코딩 검증을 안 하고 값만 저장하기 때문에(실측 확인함), mock으로 `requests.post` 자체를 바꿔치기하는 기존 스모크 테스트는 이 버그를 못 잡았음 - 실제 인코딩은 더 아래 레이어(urllib3/http.client가 소켓에 쓰기 직전)에서 일어남.

* **수정**: `X-Title` 값을 ASCII 문자열(`feed-livestock-news-issue-grouping-stage3`)로 교체, 모듈 상수(`_OPENROUTER_X_TITLE`)로 분리.
* **테스트 보강**: 자체 테스트에 `str.encode("latin-1")`을 헤더 값에 직접 호출하는 검증을 추가함 - 이게 실제 실패 지점과 동일해서, 한글로 되돌리면 테스트가 바로 재현/실패하는 것까지 확인 완료. 향후 헤더에 비-ASCII 문자가 다시 섞이면 이 테스트가 바로 잡아냄.
* 이번 59쌍도 이 버그 때문에 전부 "안 묶음" fallback으로 처리됨(파이프라인 자체는 안 죽었음, 국내/해외 Top N 결과는 정상 산출됨) - 두 버그 모두 고친 채로 재실행하면 3차가 실제로 병합하는 결과를 처음 볼 수 있음.

**3차 LLM 보조 — 첫 성공 실행 (2026-07-16)**: 위 두 버그(모델명 빈 문자열, X-Title 한글 인코딩)를 모두 고친 뒤 재실행한 결과, `provider=openrouter, model=openrouter/free`로 정상 호출되고 **애매 구간 57쌍 중 36쌍이 실제로 "같은 사건"으로 병합됨**을 실행 로그로 확인함 - 3차 LLM 보조가 구현된 이후 처음으로 끝까지 정상 작동한 사례. 결과 샘플 검증(로그 기반 정성 확인): 뉴질랜드 H5N1 관련 3개 매체 보도(0.71~0.73대 유사도)가 실제로 하나의 그룹으로 합쳐져 해외 Top5에 신규 등장(4건), 국내 계란 수입 관련 그룹도 12건 → 16건으로 증가 — 애매 구간 처리가 의도대로 작동하는 정황. 다만 어떤 쌍이 구체적으로 병합됐는지 쌍 단위 판정 로그는 아직 없어(합계만 출력) 세밀한 품질 검증은 후속 작업으로 남음.

* **1차 시도(실패, 즉시 롤백)**: 목록 페이지 URL에 캐시 버스팅 타임스탬프(`?_cb={현재시각}`)를 추가했더니, 오히려 **모든 페이지(`?page=2`, `?page=3`...)가 1페이지와 완전히 동일한 콘텐츠**를 반환하는 심각한 회귀 발생(23페이지, 276건까지 반복 확인됨) - 캐시 문제보다 심각한 버그라 즉시 제거.
* **2차 확인 - 응답 헤더 로깅 추가**: `_cb` 제거 후에도(순수 `?page=N`만으로도) 페이지마다 완전히 동일한 콘텐츠가 반복되는 현상은 그대로 재현됨. Playwright 응답 헤더(`cf-cache-status`, `age`, `server` 등)를 로그에 남기도록 추가한 결과, **모든 페이지 요청에서 `cf-cache-status: HIT`**, `age`가 요청 간격(약 23초)만큼 정확히 계속 증가하는 것을 확인 - **Cloudflare가 쿼리스트링(`?page=N`)을 무시하고 경로(`/latest-news`) 기준으로만 캐싱**하고 있음이 확정됨(안티봇 시스템의 의도적 차등 응답 가설은 이 증거로 기각).
* **추가 확인 - 캐시가 "가끔"이 아니라 "고정"돼 있었음**: 이후 실행에서 WATTAgNet이 걸린 첫 기사가 여러 번의 실행에 걸쳐 계속 동일(`"Grant Douglas to be next CFO of Inghams"`, 발행일 `2026-05-04`)로 나타남. 같은 시각 Feed Strategy는 `age`가 정상적으로 갱신되고 날짜도 최근으로 확인돼, **이 문제는 WATTAgNet 하나에만 국한**됨(Feed Strategy는 문제 없음).

  * **정정 (2026-07-22, 담당자 지적)**: 위 문장에서 "며칠째 같은 과거 캐시에 고정된 채 갱신이 멈춘 상태"라고 쓴 건 과도한 결론이었음 - Claude가 세션 초반 `web_fetch`로 직접 같은 URL을 열었을 때는 최신 콘텐츠가 나왔던 것과 모순됨. 정확한 구조는 **두 가지 서로 다른 층위의 증상을 하나의 원인이 동시에 일으키는 것**으로 정리됨:
    1. **증상 A(페이지 반복, 매번 100% 발생하는 구조적 문제)**: Cloudflare가 `/latest-news`를 쿼리스트링 무시하고 캐싱한다는 건, 그 URL 전체에 캐시 저장 칸이 물리적으로 **하나뿐**이라는 뜻 - `?page=1`이든 `?page=7`이든 전부 그 하나의 칸을 가리키므로, 한 번의 실행 안에서는 몇 페이지를 요청하든 항상 같은 내용만 돌아옴. 이건 예외 없이 항상 일어남.
    2. **증상 B(신선도, 그 시점에 뭐가 들어있었는지에 따라 달라지는 문제)**: 그 하나뿐인 칸의 내용물 자체는 시간이 지나면 갱신됨(TTL 만료 시 원본에서 재요청) - 그래서 어느 시점에 그 칸을 들여다보느냐에 따라 안의 12개 기사가 최신일 수도, 오래됐을 수도 있음. "Olymel..." 스냅샷(1~7페이지 반복 확인 당시)은 마침 12개가 전부 최근 기사였던 경우(→ 기간 이탈이 안 뜨고 30페이지까지 감, 360건 사고의 원인), "Grant Douglas..." 스냅샷(오늘 아침)은 마침 12개가 전부 5월 기사였던 경우(→ 즉시 0건).
    3. **Claude의 `web_fetch`만 최신으로 나온 이유**: Cloudflare는 지역별로 흩어진 여러 엣지 서버가 각자 캐시를 따로 들고 있음(`cf-ray` 뒤에 붙는 `-SJC`/`-MSP`/`-ORD` 등이 응답한 엣지 식별자) - GitHub Actions 러너는 특정 경로로 나가서 특정 엣지의 캐시를 계속 만나고, Claude의 조회는 다른 경로로 나가 다른 엣지의(정상 갱신되는) 캐시를 만난 것으로 추정. "사이트 전체가 두 달째 멈췄다"가 아니라 "우리 파이프라인이 타는 특정 경로 하나가 문제"라는 게 더 정확한 설명.
    4. **결론은 안 바뀜**: 설명이 정밀해졌을 뿐, 실질적 결론(쿼리스트링으로 페이지를 나눌 수 없고 이건 코드로 못 뚫음)은 그대로 유지 - 위 최종 결정(WATTAgNet `SITES`에서 제외, `SINGLE_PAGE_ONLY_SITES` 안전장치)도 그대로 유효함.
* **최종 결정**:
  1. `SITES`에서 `WATTAgNet` 항목을 주석 처리해 일시 제외(재활성화는 주석만 해제하면 됨) - Feed Strategy만 계속 수집.
  2. 캐시 무력화 목적으로 넣었던 `EXTRA_HEADERS`의 `Cache-Control`/`Pragma: no-cache`는 (a) Cloudflare가 무시하는 것으로 실측 확인됐고 (b) 전략 자체가 "캐시 결과를 받아들이는" 쪽으로 바뀌어 목적을 잃어 제거.
  3. `_collect_site`를 사이트별로 분기: `SINGLE_PAGE_ONLY_SITES = {"WATTAgNet"}`에 있는 사이트는 페이지네이션 없이 1페이지(최대 12개)만 수집(`_collect_single_page`), 나머지는 기존 정상 페이지네이션 로직(`_collect_paginated`, `MAX_PAGES=30` + `hit_cutoff`/`break` 그대로 복원)을 그대로 쓴다 - WATTAgNet을 나중에 `SITES`에 다시 넣어도 이 목록에 남아있는 한 자동으로 1페이지만 수집하도록 안전장치가 유지됨.
* **트레이드오프**: WATTAgNet이 이 상태로 계속 있으면 그 소스는 당분간 수집 불가(Feed Strategy만으로 WATT 계열 커버). 1페이지 전용 모드도 "7일 안에 12건보다 많이 나오는 날엔 일부 누락" 가능성은 감수하기로 함.
* **미해결**: WATTAgNet의 Cloudflare 캐시가 왜/언제 다시 갱신될지는 알 수 없음(사이트/CDN 쪽 문제로 추정, 우리 쪽에서 통제 불가) - 주기적으로 재활성화해서 정상화 여부 확인 필요.

**관련성 필터(2.3) - 아직 종단 간 실측 미완료 (2026-07-22 기준)**: id 기반 매칭 개선과 배치 크기 조정까지 코드로는 반영했으나, 실제 실행에서 GDELT 429 쿨다운 구간에서 로그가 끊기는 바람에 `relevance_filter`가 실제로 몇 건을 걸렀는지, 걸러진 샘플이 타당한지는 아직 한 번도 눈으로 확인 못 함 - 다음 실행에서 끝까지 완주한 로그로 반드시 검증 필요.

**전체 코드 안정성/효율성 점검 및 보완 (2026-07-23)**: 담당자 요청으로 모듈별 코드 리뷰를 진행하고, 발견된 이슈 중 일부를 실제로 반영함. 리뷰 자체(우선순위 매긴 전체 목록)는 이 세션의 대화 로그에 남아있고, 여기서는 실제로 코드에 반영된 항목만 정리.

* **`requests.Session()` 재사용**: 반복 호출이 실제로 일어나는 4개 모듈(`naver_collector.py`, `relevance_filter.py`, `issue_grouper.py`(3차), `llm_summarizer.py`)에 적용 - 기존엔 호출마다 `requests.get/post`가 매번 새 TCP/TLS 연결을 맺었는데, 세션 하나를 만들어 배치/페이지 반복 호출 전체에 재사용하도록 변경. `keyword_source.py`(실행당 1회 호출이라 재사용 이득 없음)와 `gdelt_collector.py`(내부적으로 `gdeltdoc` 라이브러리가 처리, 우리가 세션을 제어할 지점이 없음)는 대상에서 제외.
  * **부수 영향 - `issue_grouper.py` 자체 테스트 수정 필요**: `session.post`로 바뀌면서, 기존에 모듈 레벨 `requests.post`를 mock으로 바꿔치기하던 자체 테스트가 더 이상 실제 호출을 가로채지 못하게 됨 - `requests.Session.post`(클래스 메서드) 자체를 바꿔치기하는 방식으로 수정하고 재검증 완료.

* **`naver_collector.py` 안정성 - 페이지네이션 중 예외 시 데이터 손실 수정**: 기존엔 `all_results.extend(keyword_results)`가 `try` 블록 안, while 루프보다 뒤에 있어서 페이지네이션 도중(예: 3페이지째 타임아웃) 예외가 나면 이미 모은 1~2페이지 결과까지 통째로 버려졌음. `try` 범위를 네트워크 호출 부분으로 좁히고 `extend`를 항상 실행되도록 밖으로 빼서, 부분 실패 시에도 이미 확보한 결과는 보존하도록 수정. 2페이지에서 강제로 오류를 낸 시뮬레이션으로 1페이지 100건이 보존되는 것 확인.

* **`WATT_collector.py` 안정성 - 두 가지**:
  1. `_fetch_listing_page`/`_fetch_detail`의 `page.goto()`가 기존엔 `try/except` 밖에 있어서, 네비게이션 하나가 실패하면(타임아웃 등) 그 사이트/그 기사에서 이미 모은 다른 결과까지 통째로 날아가는 구조였음 - 각각 try/except로 감싸서 "목록 페이지 이동 실패 시 빈 리스트", "상세 페이지 이동 실패 시 None(그 기사만 건너뜀)"으로 통일. mock으로 둘 다 검증.
  2. `browser.close()`가 `for` 루프 뒤에 순서대로만 있어서 `browser.new_page()` 등에서 예상 밖 예외가 나면 스킵될 수 있었음 - `try/finally`로 감싸 항상 실행되도록 수정.

* **`keyword_source.py` 효율성 - 프로세스 내 캐싱**: `naver_collector`(ko)와 `gdelt_collector`(en)가 각각 독립적으로 `get_keywords`를 호출하면서 완전히 같은 CSV를 매번 새로 요청+파싱했음 - 모듈 레벨 캐시(`_cache` 딕셔너리, csv_url 기준)를 추가해 첫 호출만 실제로 네트워크 요청하고 두 번째 호출부턴 캐시 재사용. 이 프로세스는 한 번 실행되고 끝나는 구조라 캐시 무효화(stale 데이터) 걱정은 불필요하다고 판단. 자체 테스트로 두 번째 호출이 캐시를 타는 것 확인.

* **`relevance_filter.py` 효율성 - WATT 소스 자동 통과**: WATT(WATTAgNet/Feed Strategy)는 그 자체가 사료·축산업 전문지라, 이 필터가 잡으려는 오매칭 유형(동음이의어, 기관명 일부, 각주성 언급)이 구조적으로 발생하지 않는다는 담당자 지적 - WATT 소스는 LLM 배치에 아예 안 넣고 자동 통과시키도록 변경(`keyword_tagger.py`의 `site_category` 판단과 동일한 부정 조건 `source not in ("네이버", "GDELT")` 재사용, 같은 취약점도 동일하게 적용됨을 문서화). 절대적 절약 폭은 작지만(WATT 실행당 3~14건), OpenRouter 하루 한도가 빠듯한 상황에선 의미 있는 절약. WATT 2건이 배치 없이 자동 통과되는 것 스모크 테스트로 확인.

* **`issue_grouper.py` 안정성 - 3차 LLM 보조에 id 기반 부분 복구 이식**: `relevance_filter.py`에 먼저 적용했던 개선(위 2.3 섹션 참고)을 3차 그룹핑 보조에도 동일하게 적용 - 기존엔 "출력 개수 ≠ 입력 개수"면 배치 전체를 버려서, 2026-07-22 실측에서 52쌍이 429로 전멸하는 등 손실이 컸음. 프롬프트에 `id` 필드를 추가해 응답을 id 기준으로 매칭하고, 어긋난 것만 안전한 기본값으로 처리, 나머지는 정상 판정을 살림. **기본값 방향이 relevance_filter.py와 반대**라는 점 주의 - 여기는 "애매하면 안 묶음(false)"이 안전(9.4 원칙). 자체 테스트(mock)도 id 포함하도록 수정해 재검증, 별도로 "5쌍 중 1개 id 누락" 시뮬레이션도 통과 확인.
  * **효율성 검토(적용 보류)**: 2차 유사도 매칭(`stage2_group`)의 `combinations(range(n), 2)` 이중 순수 파이썬 루프를 numpy 벡터 연산(`np.argwhere` 등)으로 대체하면 대규모(수천 건)에서 유의미하게 빨라질 것으로 분석됨 - 다만 결과 동일성 재검증이 필요한 리스크가 있고 지금 규모(수백 건)에선 체감 차이가 없어 **적용은 보류, 기사 수가 실제로 커지면 그때 반영**하기로 함.

* **`storage.py` 안정성 - 파일 쓰기 실패 흡수 + 로깅 보강**: 기존엔 `main.py`가 `storage.save_week()` 호출을 `try/except`로 안 감쌌고, `storage.py` 내부 파일 쓰기(`open`/`json.dump`)도 무방비라 디스크 문제 등으로 하나만 실패해도 이미 끝난 수집/스코어링/요약 결과까지 프로세스 크래시로 다 날아갈 위험이 있었음. `week_dir()`(디렉토리 생성 실패 시 로그+None), `save_raw`/`save_scored`/`save_summary_md`(파일 쓰기 실패 시 로그+None, 개별적으로 실패 흡수) 전부 방어 추가, `save_week()`이 어떤 파일이 성공/실패했는지 요약 로그를 남기도록 함(부분 성공 지원 - 예: raw.json만 실패해도 scored.json/summary.md는 정상 저장). `main.py`의 호출부도 9.1 원칙과 같은 방향으로 `try/except` 한 겹 추가. 정상/디렉토리 생성 실패/파일 하나만 실패 세 시나리오 전부 테스트로 검증 완료.

**GDELT `requests` 전역 부작용 재설명 - 영향받는 모듈 증가 (2026-07-23, 담당자 질문)**: `gdelt_collector.py`가 import 시점에 `requests.utils.default_headers`/`requests.sessions.default_headers`를 오버라이드하는 것(2026-07-16 User-Agent 주입 대응, 위 gdelt_collector 각주 참고)은 프로세스 전역에 영향을 준다고 이미 문서화돼 있었음 - 오늘 이 부작용의 범위가 어디까지인지 다시 설명 요청이 있어 재정리.

* **메커니즘**: 파이썬은 `requests` 모듈을 프로세스당 하나만 메모리에 올려 공유하므로, `gdelt_collector.py`를 한 번이라도 import하면(현재 `main.py`가 모든 collector/모듈을 한 프로세스에서 import) 그 이후 같은 프로세스에서 실행되는 **다른 모든 `requests` 호출**이 이 바뀐 User-Agent를 그대로 쓰게 됨.
* **영향받는 모듈이 어제 세션 이후 늘어남**: 원래는 `naver_collector.py` 정도만 영향권이었는데, 이번 세션에서 신설된 `relevance_filter.py`(LLM 호출), `storage.py`(git 관련이라 실제로는 `requests` 미사용)가 추가됐고, 같은 세션에서 `issue_grouper.py`/`llm_summarizer.py`도 `requests.Session()`을 직접 만들어 쓰게 되면서(위 "세션 재사용" 항목 참고) 이들도 전부 같은 프로세스 안에 있는 한 동일하게 영향받음.
* **실질적 문제는 없음**: 각 모듈이 인증에 필요한 헤더(`X-Naver-Client-Id`, `Authorization: Bearer ...` 등)는 전부 명시적으로 별도 지정하고 있어서, User-Agent가 뭐로 바뀌든 인증 자체엔 영향 없음. 실제 장애로 이어진 사례는 없음.
* **그럼에도 계속 신경 써야 하는 이유**: 코드만 보고는 "왜 relevance_filter의 요청에 GDELT용 User-Agent가 찍히지?"를 짐작하기 어려운 숨은 결합(implicit coupling)이기 때문 - 지금 당장 고칠 필요는 없지만(건드리면 오히려 리스크), 이 프로젝트를 새로 보는 사람에게 설명해줘야 할 특이사항 목록에 계속 남겨둬야 함. 코드 변경 없음, 문서 기록만.

**OpenRouter 429 - 키 재발급으로도 해결 안 됨 확인 (2026-07-23)**: 담당자가 OpenRouter API 키를 새로 발급받아 교체했는데도, 그날 실행에서 relevance_filter/3차 그룹핑/요약 전부(40회 이상) 여전히 100% 429로 실패하는 게 확인됨. `openrouter/free`가 **계정별 할당 한도가 아니라 전 세계 무료 사용자가 공유하는 라우팅 풀**이라, 키를 새로 받아도 그 공용 풀 자체가 포화 상태면 똑같이 막힌다는 게 실측으로 확정됨(Anthropic API처럼 계정별 명확한 한도가 있는 구조와 근본적으로 다름). 대응책으로 `OPENROUTER_MODEL`을 자동 라우터(`openrouter/free`) 대신 **구체적인 모델명**(예: `meta-llama/llama-3.3-70b-instruct:free`)으로 직접 지정하는 방법을 제안 - 특정 모델은 독립된 요청 큐를 쓰므로 자동 라우터 병목을 우회할 가능성이 있음. 다음 실행에서 검증 필요. 그래도 안 되면 Anthropic 키 승인이 사실상 유일한 확실한 해결책이라는 기존 결론 재확인.

**그룹핑 임계값/프롬프트 조정 및 연쇄 병합 버그 수정 (2026-07-23)**: 담당자가 유사도 디버그 CSV를 직접 보고 임계값을 조정하고, LLM 프롬프트도 두 가지 규칙을 보강 요청.

* **임계값 조정**: `THRESHOLD` 0.75 → 0.7, `BORDERLINE_MARGIN` 0.05 → 0.06 (모듈 상단 상수, 디버그 CSV 보고 담당자가 결정).
* **프롬프트 보강**: 기존 "국가가 다르면 별개 사건"(한국/미국 예시) 규칙에, **국내 지역 단위도 마찬가지**라는 규칙(경남/제주 예시) 추가. **단신 vs 종합기사 구분** 규칙 신규 추가 - 한쪽이 사안 A 하나만, 다른 쪽이 A/B/C/D를 종합해서 다루면 A가 겹쳐도 별개 사건으로 판단.
* **연쇄(사슬) 병합 버그 발견 및 수정**: 위 두 규칙을 추가하면서, 기존 3차 병합 로직(`group_issues`)이 confirmed_pairs를 단순 Union-Find로만 묶던 것의 위험성이 커짐을 담당자가 지적 - "A~B 확정 + B~C 확정"이라는 이유만으로 A~C를 LLM에 한 번도 직접 물어본 적 없는데도 A+B+C가 통째로 한 그룹이 되는 문제가 실제로 있었음(지역/단신·종합 판정은 직접 비교했을 때만 유효한 결론이라 간접 연결로 셋 이상을 묶으면 위험). 병합 로직을 `_merge_confirmed_components()`로 분리하고, 3개 이상이 연결된 경우 **그 안의 모든 쌍이 실제로 LLM에 직접 확인됐는지(완전 그래프/클리크인지)** 검증하도록 수정 - 클리크가 아니면(사슬로만 연결됐으면) 병합하지 않고 개별 유지(9.4 "애매하면 안 묶는 게 안전하다" 원칙과 같은 방향). 사슬 케이스/클리크 케이스/단순 쌍 케이스 3종 단위 테스트로 검증, 기존 자체 테스트도 안 깨짐 확인.
